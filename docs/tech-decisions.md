# 千方慧鉴 — 技术决策记录 (ADR)

本文档记录项目核心架构决策的背景、选择与权衡。采用 ADR（Architecture Decision Record）格式，每条决策独立可追溯。

## ADR-001: 双层模型架构（本地草稿 + 云端润色）

### 背景
中医辨证论治需要准确的术语表达和专业知识推理。纯云端大模型调用成本较高且存在网络延迟；纯本地小模型专业能力不足。需要在成本、响应速度与专业质量之间取得平衡。

### 决策
采用 **本地 1.5B LoRA 微调模型草稿生成 + 云端 Qwen-plus 润色纠错** 的双层调用策略，默认模式为 `local_draft_qwen_refine`。

### 理由
- **专业术语覆盖**：本地模型基于 DeepSeek-R1-Distill-Qwen-1.5B，通过 LoRA 微调学习中医专业语料（ SylvanL/Traditional-Chinese-Medicine-Dataset-SFT），保证草稿的专业术语基本正确
- **成本控制**：草稿生成由本地模型承担，云端仅用于轻量级润色，显著降低 token 消耗
- **响应体验**：草稿生成设置 2.5 秒超时保护（`local-draft-timeout-ms: 2500`），超时或失败时自动降级直走云端，保证流式输出不中断
- **可观测性**：草稿质量由 `isUsableTcmLocalDraft` 判可用性，过滤 BPE 残留与异常标记后送入云端

### 代价与权衡
- **部署复杂度**：需额外维护本地模型服务进程（FastAPI + transformers），依赖 GPU 加速以获得可接受延迟
- **草稿质量依赖**：本地模型训练质量直接影响最终输出，需持续迭代微调数据集
- **网络依赖未消除**：润色阶段仍需云端 API，完全离线场景需切换至 `local_only` 模式

### 现状与演进
- **当前实现**：支持三种模式切换（`cloud_first` / `local_draft_qwen_refine` / `local_only`），已在 `DeepSeekService.java` 中完整实现
- **演进方向**：评估更大参数量本地模型（如 7B）以减少云端依赖；探索蒸馏方案将云端润色能力下沉至本地

## ADR-002: 自研进程内向量存储替代外部向量数据库

### 背景
RAG 知识库需要支持语义检索、文档上传、相似度 Top-K 查询。外部向量数据库（如 Chroma、Milvus）引入额外部署依赖与运维成本。

### 决策
采用 **Java 进程内自研向量存储**，基于 `ConcurrentHashMap` + FLAT 索引，持久化到文件系统（`downloads/rag/vector_index.dat`）。

### 理由
- **零外部依赖**：无需部署独立向量数据库进程，降低运维复杂度
- **启动简单**：后端 JAR 包启动时自动加载索引文件，单命令即可完整拉起系统
- **满足当前规模**：题库文档规模下（千级文档块），FLAT 索引检索延迟可接受（<100ms）
- **可控性强**：存储格式完全透明，便于调试与自定义索引策略

### 代价与权衡
- **规模上限**：FLAT 索引检索复杂度为 O(n)，文档量超过万级后延迟显著上升
- **功能有限**：不支持高级索引（如 HNSW、IVF）、不支持分布式部署
- **持久化鲁棒性**：文件系统持久化需处理并发写入与崩溃恢复

### 现状与演进
- **当前实现**：`VectorStoreService` 提供插入、检索、持久化功能，已在生产环境运行
- **迁移路径**：当文档量超过 5 万或检索延迟要求 <50ms 时，评估迁移至专用向量数据库（如 Milvus）
- **短期优化**：引入简单 L2 距离缓存、批量导入优化

## ADR-003: 嵌入式 Neo4j 而非 Docker 独立部署

### 背景
知识图谱功能需要图数据库支撑实体关系存储与查询。独立 Neo4j 部署（Docker 或原生安装）增加环境准备复杂度。

### 决策
采用 **嵌入式 Neo4j**（`QfhjNeo4jLauncher`），与后端 Java 进程同进程运行，数据目录通过参数挂载（`neo4j-data`）。

### 理由
- **零配置启动**：单命令启动 Neo4j 嵌入式 JAR，无需安装、无需 Docker
- **资源隔离**：嵌入式模式端口固定（Bolt 17687 / HTTP 17474），便于防火墙配置
- **开发友好**：数据目录可直接挂载至本地路径，便于备份与迁移
- **可开关**：通过 `@ConditionalOnProperty(NEO4J_ENABLED)` 支持功能开关，降低调试成本

### 代价与权衡
- **运维能力弱**：嵌入式模式不支持 Neo4j 企业版特性（如因果集群、在线备份）
- **单机限制**：无法水平扩展，图规模受单机内存限制
- **版本绑定**：Neo4j 版本与后端 JAR 强绑定，升级需同步变更

### 现状与演进
- **当前实现**：`TcmKnowledgeGraphService` 从 MySQL `questions` 题库同步实体建图，前端 `TCMKnowledge.tsx` 可视化展示
- **演进方向**：图规模超 10 万节点时，评估迁移至独立 Neo4j 部署（Docker Compose）
- **短期优化**：引入图谱统计缓存（当前 5 分钟）、批量同步优化

## ADR-004: 七步向导 FSM 辨证而非纯自由对话

### 背景
中医辨证需要结构化采集多维度信息（症候程度、子午归经、六经传变、合病合方等）。纯自由对话难以保证信息完整性，用户易遗漏关键步骤。

### 决策
采用 **七步向导式有限状态机（FSM）辨证流程**，后端 14 张 `wizard_*` 表支撑会话状态，前端约 3000 行 `WizardDiagnosis.tsx` 引导用户完成七步采集。

### 理由
- **结构化采集**：每步聚焦特定维度（症候程度、时辰经络、六经传变、AI 辨证、合方加减、疗效评估、专家会诊），保证信息完整性
- **可解释性**：每步输出可追溯推理路径（如八纲辨证结果、脏腑经络关联），符合中医临床思维
- **会话持久化**：状态表支持中断恢复，用户可分多次完成辨证
- **多流派复核**：第七步提供伤寒、温病、脏腑、经络四流派 AI 交叉复核，增强结论鲁棒性

### 代价与权衡
- **灵活性受限**：用户无法跳过步骤，复杂病例可能需要循环往复调整
- **表结构膨胀**：14 张状态表增加数据库维护成本
- **前端复杂度高**：3000 行单文件组件需进一步拆分（演进目标）

### 现状与演进
- **当前实现**：七步流程完整实现，支持 PDF 导出与免责声明
- **演进方向**：引入"自由对话+向导补全"混合模式，允许用户先自由描述再由系统补全缺失维度
- **重构优化**：前端组件拆分为多步骤独立模块，降低单文件复杂度

## ADR-005: 皮肤检测独立 Python 服务

### 背景
皮肤病检测需要深度学习模型（Swin Transformer + DABNeck + MSDAH）进行图像分割，依赖 PyTorch 与 GPU 加速。Java 生态缺乏成熟的医学图像分割库。

### 决策
将皮肤检测拆分为 **独立 Python FastAPI 服务**（端口 5000），通过 HTTP 内网通信与后端交互。

### 理由
- **技术栈分离**：Python 服务专注医学图像处理，Java 后端专注业务逻辑与数据持久化
- **GPU 隔离**：Python 服务独占 GPU 资源，避免与本地模型服务（端口 8000）竞争显存
- **独立迭代**：模型升级（如更换架构、调整损失权重）无需重启 Java 后端
- **多模态集成**：分割掩码送入 Qwen-VL-plus 进行多模态分析，形成中西医结合意见

### 代价与权衡
- **部署复杂度**：需额外维护 Python 环境与依赖（PyTorch、timm、权重文件）
- **网络开销**：图像上传与掩码返回增加 HTTP 延迟（内网通信可控制在 200ms 内）
- **错误处理**：需处理服务不可用、超时、权重文件缺失等异常

### 现状与演进
- **当前实现**：`skin_service/main.py` 提供分割接口，后端 `SkinDetectionController` 协调多模态分析
- **演进方向**：引入模型版本管理、A/B 测试框架；评估 TorchServe 替代 FastAPI 以提升吞吐
- **短期优化**：添加请求队列、批处理支持以提升 GPU 利用率

## ADR-006: 知识图谱与向量检索独立双引擎

### 背景
系统同时具备 Neo4j 知识图谱（实体关系可视化）与 RAG 向量检索（语义搜索）。两者适用场景不同：图谱擅长关联推理，向量擅长语义匹配。

### 决策
采用 **双引擎并行架构**：图谱与向量检索各自独立工作，前端提供两个入口（`TCMKnowledge.tsx` 与 `TCMDiagnosis.tsx`），暂不实现融合查询链路。

### 理由
- **场景分离**：图谱用于知识探索（如查看某穴位关联的脏腑经络），向量用于内容检索（如搜索"肝阴虚"相关文档）
- **技术简单**：避免构建复杂的融合查询编排层，降低系统复杂度
- **性能隔离**：两个引擎独立部署与扩容，互不影响
- **快速交付**：并行开发可更快验证两个功能的价值

### 代价与权衡
- **用户体验割裂**：用户需手动选择图谱或检索入口，无法获得"关联+语义"的综合结果
- **数据一致性**：图谱实体与向量文档需分别维护，存在不一致风险
- **重复存储**：同一份知识在图谱与向量库中各存一份，存储成本增加

### 现状与演进
- **当前实现**：`TcmKnowledgeGraphService` 提供图谱查询，`RagService` 提供向量检索，两者无交互
- **演进方向**：融合检索列为演进方向——探索图谱引导向量检索（如通过实体约束缩小检索范围）、向量结果补充图谱（如通过文档相似度发现隐含关系）
- **短期优化**：统一前端入口样式，提供快速切换体验

## ADR-007: 前后端分离 + JWT 无状态认证

### 背景
系统需支持多终端访问（Web、移动端）、多用户权限管理（普通用户、管理员）。单体架构难以满足前端独立迭代与后端服务复用的需求。

### 决策
采用 **前后端分离架构**：前端 React 18 + TypeScript + Vite（端口 5173），后端 Spring Boot（端口 8081），通过 JWT 无状态认证。

### 理由
- **技术栈分离**：前端团队专注交互体验，后端团队专注业务逻辑与数据安全
- **独立部署**：前后端可独立构建、发布与扩容，提升迭代效率
- **无状态认证**：JWT Token 避免 session 共享问题，便于水平扩展
- **标准化接口**：RESTful API 设计便于未来接入移动端或第三方调用

### 代价与权衡
- **部署复杂度**：需同时维护前端构建产物与后端 JAR 包，增加部署步骤
- **跨域配置**：需处理 CORS 预检请求与 cookie 策略
- **Token 管理**：JWT 无法主动失效，需依赖短过期时间 + 刷新令牌机制

### 现状与演进
- **当前实现**：`JwtUtils` / `SecurityConfig` / `JwtAuthenticationFilter` 完整实现 JWT 认证，支持注册/登录/邮箱验证/忘记密码
- **演进方向**：引入刷新令牌（refresh token）机制；支持 OAuth2.0 第三方登录
- **短期优化**：完善 Token 黑名单机制（基于 Redis），支持用户主动登出
